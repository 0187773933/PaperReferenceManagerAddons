# Paper Reference Manager Addons

## Addons

1. `prma` : alias for `prma server --watch` — launches the live server (exists endpoint + dashboard) with the background auto-processing worker on. (Run `prma server` without bare-command for the server with `--watch` off.) Or `prma --exists` for **minimal mode** — the userscript endpoint and nothing else (see `prma server --exists` below).
1. `prma main` : the base pipeline — refresh the snapshot, then update the OpenAlex cache (meta + cited-by + references) for **every** library paper. This was the old no-subcommand default.
1. `prma missing` : generates missing.xlsx
1. `prma check-missing-file <log.md>` : which papers in a Markdown **research log** aren't in the library. The log is the dated notebook you keep while reading — `# 03SEP2026` headings, and under each a run of `&nbsp;`-separated blocks with a paper's title on one line and its link(s) below. Every block is one paper; its DOI is lifted out of the link (doi.org, publisher article routes, bioRxiv, ezproxy'd copies of all of those) with the browser debris cut off (`.full` / `.abstract` / `v1` / MIT Press's trailing article number), since a DOI with junk on the end is one the library will never match. Each is then checked with the **same policy as the `/exists` userscript endpoint** (`server.lookup` — a DOI settles it, otherwise the title is fuzzy-matched at the same cutoff), run in-process on the manager snapshot so no server needs to be up. A DOI miss is retried by title before it counts as missing (a preprint DOI on the note, the journal version in the library) and those recoveries are listed separately, since a DOI that doesn't match is worth a glance. Output `output/check-missing/<log-stem>.md` — the missing papers with the log's date, line number and link, plus how many times the log mentions each (`--out` to put it elsewhere). `--list-only` prints what the parser extracted as JSON and checks nothing, for when a log's layout drifts. For one-off lookups from a shell there's `unix-scripts/Exists.sh <doi-or-title> …`, which asks the running server the same question.
2. `prma server` : runs the local HTTP server — the 'exists' endpoint for browser userscripts (`POST /exists`) **and** the full-text-search dashboard (`GET /`) for the **external papers you don't have**: works your library cites but you're missing, and works that cite your library. (Your own papers live in Zotero — they're indexed only for identity, to know what to exclude.) **Search** folds the text and your query the same way before matching — accents stripped and every punctuation mark (colons, slashes, hyphens, en/em dashes, curly quotes) flattened — so `MindAlign: Decoding Inner Speech`, `EEG–fMRI` and a pasted `10.1002/(SICI)1099-1492(199908)12:5` all find their paper (DOI, record key and journal are searchable too). Results are **ranked by relevance** by default whenever there's a query: the query as the *title* outranks the query buried on page 9 of a much-cited paper, with citations only breaking ties (click any column to rank your own way). If nothing matches at all, it falls back to the closest titles and says so. The dashboard serves the index that `prma reindex` persists to disk: it loads instantly and auto-reloads when you re-run reindex. If no index exists yet, it builds one lazily on first open. Pass `--watch` for **live processing**: a background worker detects papers you add to Zotero/Mendeley, runs the full per-paper suite on each (openalex → yolo → ocr → images → methods → code → md → datasets), and rebuilds the index so new papers appear automatically — the dashboard shows a live progress toast (polled from `GET /api/jobs`). Add `--watch-summarize` to also run the LLM summary on each. The same server hosts two **hand-curation boards** for building your premier-reference list by hand: search your library from the page (`↵` or double-click a hit adds it), drag rows to sort them, tag each with modalities (autocompleted from `config/methods.py`, pre-filled from the `prma modalities` stamp) plus your own click-to-paint tags, type into as many free-text columns as you want, delete anything with one click (the toast undoes it), and import / export the whole thing as CSV — every row carrying the same DOI / proxy / PDF / figures / MD / Methods links the dashboard shows. `/sort`'s `⇩ Import CSV / Sheet` also takes a **Google Sheet** by its link (fetched server-side by `POST /api/sheet/csv`, `src/db/gsheet.py`; the sheet must be shared *Anyone with the link*) or the CSV it downloads as, and that import is **add only**: new papers are added, papers already on the board only gain missing tags and fill empty cells, nothing is removed or overwritten, and you choose between the sheet's order (default — papers only on the board ride with the row above them) and appending the new ones to the end. You tick which columns come in (the sheet's Notes / Added by / Methods evidence are off by default); new ones — Methods summary, Datasets, Code — arrive **folded** behind a `▸ Show Extra Columns` button in the button row, and with them out the board scrolls sideways under a pinned # / Paper column. The boards' search **matches titles** by default (`mode=title` on `GET /api/search`): type any piece of a title and the closest titles come back, best first — nothing has to match exactly, so a typo, a missing word or two words the wrong way round still land the paper (a pasted DOI or record key jumps straight to it), and the dropdown switches to the dashboard's boolean full-text search when you want to hunt a phrase instead of a paper. `/sort` adds the case search can't cover: **`🆕 Recently added`** lists the newest papers in your reference manager (last 10 by default, `show 25` / `50` in the list) in that same hits list, so you add them the same way — and it reads **Zotero itself** (`GET /api/recent` → `tasks.snapshot.recent`, cached on the same source mtime the `/exists` endpoint watches), *not* the dashboard index. That is the point: a paper only becomes searchable once a snapshot has filed it into `output/cache/papers/` and `prma reindex` has read it, so until then searching for one you just saved finds nothing — this has it seconds after you save it, keyed the way the pipeline will key it. One the index has never seen is flagged `not indexed yet`: it adds with no tags and empty Code / Datasets cells, and both fill themselves in once it has been processed. Both boards **number every row and let you type into that number**: press `↵` and the paper goes to that position (its tier's, on `/tiers`) — no scrolling, no dragging. And you can **click a row to select it** (`⌘`-click adds another, `⇧`-click takes the range) and then click chips at the top to flip tags / modalities on and off the whole selection; with nothing selected, clicking a chip still arms it for click-to-paint, and `Esc` clears either. `🔎 Filter` turns that same chip bar into a **filter** — click tags and the board narrows to the papers carrying them (`any` / `all` switches whether one is enough), on top of the text box that matches anything typed anywhere in a row. Every tag and modality is drawn in **its own pastel**, so a row's chips are a pattern you read at a glance rather than five words you parse: a new one takes the next unused colour by itself, `🎨 Colours` is where you change them, and the choice lives in the document (`vocab.tags` / `vocab.mods`) so it follows the board to every browser. The chip bar itself is **rearrangeable by hand** — drag a chip along it and it stays where you put it, so you can group the ones you think of together (a chip only moves within its own bar; modalities and tags are separate vocabularies). That order is `vocab.tags` / `vocab.mods` order, i.e. part of the document, so a grouping you build is the same in every browser and after a restart, and a plain click still arms / filters / tags as before. Both boards also **import somebody else's bibliography**: `📋 Import refs` takes a reference list **pasted** in, or a **`.docx` / `.txt`** dropped on the panel, and reads it back into papers (`src/db/refparse.py` — numbered or not, AMA / Vancouver / APA / IEEE, wrapped across lines or one paragraph each; a `.docx` is unzipped and read server-side, so nothing has to be converted first). Each reference is resolved against your library by DOI, then by title, so one you already have arrives carrying **its real key** — every DOI / PDF / figures / MD / Methods link works, and its `prma modalities` stamp is pre-filled — while the rest keep whatever the parse got, picking up a WID and an open-access PDF url from the missing-paper pools where one matches. **Only what's new is taken**: anything already on the board, or already staged, is counted and skipped, so re-pasting a list you've grown brings in the difference and nothing else. Nothing lands on the board itself — it goes to a **staging shelf** above it, out of the sort and out of every tier, where you fix a mis-parsed title, tag rows one at a time or check several and tag them together, and only then press `＋ Add` (to the bottom of the sort list, or the bottom of the `◉ target` tier). A staged row is **the row it is about to become** — same chips *and the same free-text columns* — so a note you have while reading a reference is typed once, on the shelf, and rides onto the board with it; and **adding leaves you on the shelf** (the row flashes wherever it landed, but the page doesn't chase it), so working down an imported list is one pass instead of a scroll back for every row. The shelf is part of the document (`staging`), so a reload — or the other tab — still has it, and a CSV *Replace everything* leaves it alone. Neither board can lose what you typed into it: every change is mirrored into the browser and only dropped once the server confirms the save, a failed save retries by itself, closing the tab pushes one last copy out, and the next load **offers to restore** anything that never made it — while on disk each document is written atomically and, if a crash ever leaves one unreadable, recovered from its newest history snapshot instead of coming back empty. A row's chips are stored and shown **alphabetically**, so a paper reads the same way every time you look at it, and titles on both boards are plain text — as links they took the browser's visited colour the moment you opened a paper from any other prma page, so the link strip under each title is what opens it. **`GET /sort`** is one numbered list in the order *you* drag it into — no groups: what a paper is you say with tags (`fMRI`, `EEG`, both, or anything you invent, all saved with the board), where it sits you say by dragging. A paper added from search arrives already tagged from its Methods stamp, and with its Code / Datasets cells written from what `/code` and `/datasets` found for it — one link per line, a named dataset as `name — its home page` — wherever those cells are empty. `⇩ Import CSV / Sheet` reads a Google Sheet by its link **with the links behind its cells** (the Datasets / Code labels come in as their full URLs — a CSV download would carry only the labels), and can be re-run whenever the sheet changes: per column you choose *fill empty cells*, *overwrite* or leave it out, and for tags *add missing* or *replace*, each choice showing how many cells it would change first — and the list keeps its own order unless you ask for the sheet's. **As little as possible sits between the title and the tags**: one pinned line — the board, its counts, the links to the other pages, what's filtered or selected, help, theme, save state — and then just two rows of tools, one for what happens to the board (papers in, papers out, the order, what tagging does, the columns, and what you're looking at — the newest papers in the library, and the text filter) and one for finding a paper. The tools and the tag bar scroll away with the list so a long list gets the whole window, and `/` brings the search back down over it from anywhere without moving it, putting itself away when you scroll on or press Esc. The tag bar's own `+ new tag` / `🔎 Filter` / `🎨 Colors` trail the chips rather than heading them, so they take what is left of the last chip line instead of a line of their own. **Any URL in a free-text cell is a live link** — one you typed, or one `＋ Add` and the sheet import wrote into Code / Datasets — and clicking it opens that page in a tab *behind* this one, so three repos open in a row without losing your place; the cell stays an ordinary box of text (click the words and the caret lands where you clicked), and what is saved and exported is still the plain text, links and all. Tagging never reorders anything unless you turn on `⇥ Auto-move`, and `⇅ Order by…` reorders the whole list once (by tags, year, citations, title, date added) with an undo. **`GET /tiers`** is the sibling with buckets: tiers you place papers into, ranked S–D or whatever you rename them to. They keep separate documents (`output/cache/sort.json` / `tiers.json`, every replaced version kept under `output/cache/sort-history/` / `tiers-history/`), so they follow you across browsers like the figure-report picks do; `⇄ Pull from Tiers` copies the tier board's papers into the sort board. **`--exists` is minimal mode** — the opposite end: serve only what the browser userscripts poll (`POST /exists` + `GET /api/version`, plus `POST /refresh`) and nothing else. No dashboard index is loaded or built, no figure reports, and no per-paper processing forked off when you add papers to your library (it forces `--watch` off). Every other route answers `503` with an explanation instead. For when you just want the "do I already have this paper" coloring in the browser without running the whole pipeline. Works as `prma --exists` or `prma server --exists`.
3. `prma reindex` : refreshes the OpenAlex cache (snapshot + fetch new papers, download only), then (re)builds the dashboard's **own** full-text search index by streaming the OpenAlex cache off disk, and persists it. Independent of `missing.xlsx`. Incremental — adding papers only re-reads the new papers + their new references, not everything (`--full` to rebuild from scratch, `--skip-snapshot` to index the existing cache without re-fetching).
4. `prma snapshot` : creates local archive file
5. `prma yolo` : run doclayout yolo model on each pdf
6. `prma images` : generate individual images and a montage from figures and tables in each pdf
7. `prma ocr` : run ocr task on yolo blocks
8. `prma md` : generate markdown versions of each pdf
9. `prma text` : generate text versions of each pdf
10. `prma methods` : isolates methods sections of each pdf
11. `prma summarize` : runs summarization task on each pdf or section
12. `prma rollup` : generates a report from summarization tasks
13. `prma crawl` : attempts to crawl the OpenAlex graph
14. `prma code` : scans each paper's OpenAlex abstract + OCR text for **source-code / data links** (GitHub, GitLab, Bitbucket, OSF, Dryad, Zenodo, Figshare, Code Ocean, Hugging Face, …), reconstructing URLs the OCR split across lines and dropping dead/duplicate fragments. Pins the unique links on each record so the dashboard shows a sortable **Code** column (after Links, In-Library tab) and `prma md` can render a `## Source Code` section, and rolls everything up into `output/code/code.xlsx` (three sheets: *Links by Paper*, *By Paper*, and *Unique Links* — the last aggregating each link to the DOIs that cite it + a paper count; every per-paper sheet carries DOI / proxy / pdf links plus date-added and publication date). **GitHub / OSF enrichment:** if `config.yaml` has a `github.api_key`, it also fetches every unique GitHub repo's metadata + README (cached under `output/cache/github/`) and tags each by neuroimaging method (**fMRI / EEG / ECoG / fNIRS / MEG / PET / EMG**) — the *Unique Links* sheet gets a column per method (plus a combined *Methods* column on every sheet) so you can sort/filter to the fMRI repos first. With an `osfio.api_key` it does the same for every unique OSF (osf.io) node — resolving each GUID via the OSF API and pulling its metadata + Home wiki (cached under `output/cache/osf/`) — so OSF projects, registrations, and preprints get method-tagged too. **Method inference from citing papers:** a link is also tagged with the modalities of the papers that link it — the same keyword scan runs over each citing paper's abstract + isolated **methods section** (`prma methods` output, or the `## Methods` slice of the rendered md; *not* the full OCR, whose reference list would false-positive every cited modality) — so a repo whose README never names a method still inherits it from the fMRI / EEG / … studies that use it. The *Unique Links* method columns mark provenance: **✓** = confirmed in the repo/node README, **·** = inferred only from the citing papers. **OCR link repair:** GitHub links the OCR mangled (a truncated `…/Surfa` or merged `…-TOSTART-…`) 404 on fetch; rather than drop them, it lists the owner's *real* repos (cheap — the core API rate limit, not Search) and fuzzy-matches the broken name (`exact`/`prefix`/`fuzzy` tiers), then pins the corrected link so `code.xlsx` and the dashboard show the working repo (with an *OCR Fix* audit column / dashboard tooltip spelling out the original + match confidence, so a wrong guess is easy to spot). Runs OCR inline (idempotent) so it's one-stop. `--force` re-scans every paper and rebuilds the workbook from the **cached** GitHub/OSF data (no re-download — fast, for iterating on the scan/tagging logic); `--force-download` additionally re-fetches that cached metadata and re-runs link resolution over the network (the two are independent — combine them for a full refresh). Also runs automatically as the `code` stage of the per-paper suite (see below), so papers added under `prma server --watch` are scanned on the fly. **The page:** the server serves **`GET /code`** — one row per paper `prma code` found a repo for, with the repo links themselves and a column for each curated surface that holds it (**Review** — included / screened out, **Sort**, **Tier**, **Figs** — how many of its figures you picked on `/images`), so *"which of the papers in my review actually ship code"* is a click on a column header rather than a search. Sort by any column, filter by those same memberships, by code host (GitHub / OSF / Zenodo / …) or by anything typed — titles, DOIs, tags and the repo URLs themselves are all searchable — then export exactly what you are looking at, in the order you put it in, as **.xlsx** (two sheets: one row per paper, one row per link) or CSV. Everything on it is read off what is already in memory — the record's own links, the two board documents, `output/cache/review.json` and the `/images` picks — so it costs nothing to open and never re-derives what code a paper has.
15. `prma datasets` : `prma code`'s sibling for the other half of the question — not *does this paper ship a repo* but **what public data does it stand on**, which in this literature is almost never the authors' own upload. Two kinds of evidence, because papers give it two ways. **Archive links** are the records a paper actually printed, harvested out of its OpenAlex abstract + OCR full text: OpenNeuro, NeuroVault, DANDI, OpenfMRI, OSF, Zenodo, Dryad, Figshare, Hugging Face, PhysioNet, Dataverse, NITRC, CRCNS, EBRAINS, BALSA, ConnectomeDB, LONI/IDA, NDA, ABCD, UK Biobank, Synapse, G-Node, Mendeley Data, Kaggle, … — through the *same* extractor `prma code` uses (`src/tasks/code.py` exports the URL machinery; only the host table differs), so URLs the OCR split across lines are rejoined and dead fragments dropped, and a versioned OpenNeuro DOI (`10.18112/openneuro.dsXXXXXX`) is caught as OpenNeuro rather than read as one more paper DOI. Plus **bare accessions** — `ds000105` printed with no URL around it, which is how most papers cite one — minted into the canonical `openneuro.org` record and marked as recovered rather than quoted (a superscript ˟ on the page, a *From Accession* column in the sheet), and de-duped against any real URL for the same accession. **Named datasets** are the collections a paper only *names* — HCP, NSD, ABIDE, ADNI, UK Biobank, ABCD, BOLD5000, THINGS, Algonauts, StudyForrest, Narratives, … — matched against the same vocabulary `/review` screens with (`src/review/datasets.py`), so a paper's datasets read identically on both pages; read off the rendered md with the **bibliography cut** (a reference list is a list of other papers' titles and half of them name a dataset the paper never touched), falling back to the isolated methods section + abstract when nothing was rendered. Code forges are deliberately *not* in the table — a GitHub repo is a `/code` link — while the generalists that host both (Zenodo, OSF, Dryad, Figshare, Hugging Face) appear on both pages, which is the honest answer about what they are. Runs `prma md` inline (idempotent, and it pulls each paper up through yolo → ocr → preprocess → images → code on the way) so it's one-stop, and also runs as the `datasets` stage of the per-paper suite (after `md`, whose output the name pass reads), so papers added under `prma server --watch` are scanned automatically. `--force` re-scans papers already marked done. **The page:** the server serves **`GET /datasets`**, which reads the scan *both ways round*. **Datasets** — one row per collection, with how many of your papers use it, how many of those made it into the review, onto `/sort` and into a tier, and the year span they cover; each row reads name → **what it is** → where it lives → the earliest paper in your library that used it (with DOI / proxy / PDF / md links), and expands to the full roll call. The description line spans the table rather than the Dataset column, since a sentence in a 380px cell wraps to five lines; for a named collection it is a written one-liner in `src/review/datasets.py`; for an archive record it is **fetched once and cached** under `output/cache/datasets/` — Zenodo, Figshare, OpenNeuro and OSF through their own keyless APIs, everything else by reading the page's `<title>`. Dead links and soft-404 titles are dropped, and a timeout or a 5xx is deliberately *not* cached so it retries on the next run rather than being blacklisted by one bad minute. The fetch uses an honest User-Agent on purpose: Zenodo's API answers a plain one and **403s a spoofed browser string**. `--no-fetch` skips the network entirely; `--force-download` re-fetches. That is the question none of the other pages can answer: what this library is actually built on. **Papers** — one row per paper, `/code`-shaped, with the data it names — archive records link to what the paper printed, and a collection the paper only *named* links to its home page (one checked URL per name in `src/review/datasets.py`; a name with no entry stays plain text rather than becoming a guess) — a Code count that jumps to `/code`, and the same Review / Sort / Tier / Figs columns. Filter by *has a link* vs *named but unlinked* (the papers where finding the data is on you), by *ships code* (data **and** code), by any curated surface, by archive, or by anything typed — then export exactly what you filtered to as **.xlsx** (two sheets: one per paper, one per paper-and-dataset) or as a CSV of whichever table you're looking at. Everything on it is a dict merge over what is already in memory, so it costs nothing to open and never re-derives what data a paper used.

16. `prma process <doi-or-title>` : find ONE paper in your manager (by exact DOI or fuzzy title) and run the full per-paper suite on just it — snapshot → openalex → yolo → ocr → images → methods → code → md → datasets — then reindex so the dashboard refreshes. The library tasks are idempotent and scoped to the single paper, so this is fast. `--summarize` also runs the LLM summary. Same code path the server's `--watch` worker uses per newly-added paper.
17. `prma reprocess <doi-or-title>` : `prma process` with `--force` on — **redo** every stage on one paper instead of skipping the ones already done. Reach for it when you **replaced a paper's PDF** (the published version swapped in for the preprint / manuscript you first added): the DOI never changed, so the snapshot sees nothing new, every stage finds its old output and skips, and the server's `--watch` backlog counts the paper as done — nothing in the pipeline notices the new file on its own. It deletes what the pipeline derived for that paper (`output/md`, `output/methods`, `output/text`, its figure crops + montages under `output/images`, and the derived record fields — `yolo` / `sections` / `raw_text` / `images` / `code` / `modalities` / the `processed` stamp), then runs the suite normally so each stage rebuilds from the PDF on disk *now*. Identity (`doi` / `title` / `sources`) and the OpenAlex cache are untouched; LLM summaries are kept unless you also pass `--summarize`, which regenerates them. Prints the PDF path it's about to work from — worth a glance, since a Zotero item holding **several** PDFs resolves to the first one that exists on disk, not the newest. (Not to be confused with `prma reindex`, which rebuilds the dashboard's search index for the whole library and runs no pipeline stages.)

18. `prma review` : builds the **literature review** the server serves at **`GET /review`** — what `/sort` and `/images` *add up to*. Those two pages are judgements (this paper is worth keeping; this figure is worth looking at) and neither says anything about what the papers **contain**; this takes their union and reads the text `prma md` and `prma methods` already wrote. Every candidate is **screened against three criteria**, all of which must hold: fMRI/BOLD is the *dominant* modality in its methods (an EEG/MEG/ECoG/fNIRS paper that merely mentions fMRI is out), the paper **decodes** (fMRI in, stimulus / mental content / class label out — encoding models and MRI reconstruction / acceleration are out), and transformer or attention machinery sits inside the model **the authors built** (citing Vaswani in related work is not enough). What survives gets every architecture, acquisition and preprocessing detail its own text states pulled out — layer counts, heads, embedding dims, backbones, losses, optimiser, LR, TR, TE, voxel size, slices, atlas, smoothing, and forty-odd more — and **every value carries the verbatim sentence it was parsed from**, so nothing on the page has to be taken on trust; click a value and the quote opens under it. Values that are physically impossible for human fMRI (a 565 ms echo time, a 40 mm voxel) are dropped by plausibility gates, and where a paper states a parameter more than once the values are ranked by how often it says it. **A blank means the paper does not say it**, never that the value is zero, and the page prints those words rather than leaving a cell empty to be misread. Most deep-learning papers never state scanner settings at all — they say "we use NSD" and move on — so acquisition blanks are filled from a **consensus mined out of the whole corpus** for the public dataset that paper uses, marked *from dataset* and naming how many papers back it; a paper using several datasets is left blank rather than guessed. Hand-verified detail in `config/review-overrides.json` (keyed by the same DOI / record key the boards use) overrides the extraction and flags the row. The page **orders the list the way every other prma surface does** — recently added, publication date, year, citations, title, model name, each reversible — on top of the default (priority, then newest), and puts the citation count and the date the paper entered your library on the row itself, so a list ordered by a fact is a list you can see that fact in. (*Recently added* is prma's own `created_at`, the same date the figure reports' "Recently added" uses — when *prma* first filed the paper, which is not `/sort`'s `🆕 Recently added` button: that one reads Zotero's own `dateAdded` off the live library, because its whole job is the papers prma has not filed yet. Papers missing a sort key always fall to the bottom rather than clumping at the top as a run of blanks, in either direction.) It **follows your light / dark setting** — the shared `prma-theme`, so flipping it here flips the dashboard and both boards too. It filters by priority (1 = inner/imagined speech, the bullseye), task category, and whether a paper is on the sort board, has picked figures, is human-curated or ships code; every row carries the same link strip as the rest of prma — DOI / Proxy / PDF / MD / Methods / **Figures** (the `prma images` montage), on the excluded rows too, where flicking through a borderline paper's figures is the fastest way to check the screener was right; it exports what you're looking at as JSON or CSV; and it shows **what was excluded and why**, with the **borderline** ones — dropped only for weak attention evidence — flagged, because that is where a false negative hides. Output `output/cache/review.json`; the same build is the Rebuild button on the page. **Slow**: a regex pass over every candidate's full text, minutes on a few hundred papers, so it is never run on the way to serving the page — the server hands you the last build, says when the boards have moved since, and rebuilds in the background while you watch the progress bar.

19. `prma review-missing` : the **same three criteria, run over the papers you do not have**. `prma review` screens a judgement — the few hundred papers somebody put on `/sort` or picked a figure from. This screens the *other* pool: the dashboard's **All missing** tab, every work your library cites plus every work that cites it, ~140,000 papers nobody has judged. There is no full text for any of them, so each is screened on the only thing there is — its title and its OpenAlex abstract, ~1,500 characters against the 50,000 `/review` reads. The **vocabulary is reused verbatim** (`src/review/classify.py` — one place decides what counts as fMRI evidence, on both pages); only the thresholds move, and each moves for a stated reason: fMRI gets *harder* to establish (an abstract names its modality once if at all, so one mention counts and dominance becomes "named at least as often as any rival" rather than a ratio over hundreds of hits), while attention gets *easier to trust* (an abstract has no related-work section, so a transformer named in it is almost always the authors' own — one mention, where the full text needs two). **What that costs is measured, not asserted**: screened against the papers the built `/review` has already judged, it is right about roughly **nine in ten** of what it lets through, and finds roughly **two in five** of what the full text included. The recall is **re-measured on every build** — the same screen re-run over the papers `/review` included — so the page prints today's score rather than a number written down once (precision can't be: it needs the papers `/review` threw out, and an excluded row carries no abstract to re-screen, so that one is recorded with its basis beside it). That asymmetry is not a tuning failure — most of the misses are papers whose abstract never names an architecture at all, and no threshold recovers a word that isn't there. So the page reports **candidates, never a review**, and prints both numbers at the top of itself rather than in a footnote. What survives gets the same field extraction over its abstract, every value behind the verbatim quote it came from, and acquisition blanks filled from the **dataset consensus `/review` already mined from your own corpus** (so a missing paper that names NSD is still told what NSD's TR is, marked *from dataset*). The excluded are **tallied rather than listed** — 97,000 rows is not a table, it is the pool again — but the **near misses** are kept: papers that satisfied two criteria and failed exactly one, read off each criterion's own verdict rather than off the first test that failed, ranked by how many of your papers connect to them. That is `/review`'s *borderline* idea at this scale, and where a false negative hides. **The page:** the server serves **`GET /review-missing`**, drawn by the same renderer as `/review` (the shared furniture moved to `/static/review.css` when the second page needed it) with three deliberate differences — only *filled* fields are drawn and the blanks are counted, since an abstract states a backbone and essentially never a TR; the excluded are a tally with the near misses underneath; and every row leads with **how many of your own papers connect to it**, which is the one ranking this pool has that a literature search does not and the default sort. Filter by pool (in bibliographies / newer-citing / both), by connectivity, by priority, task, named data or having an open-access PDF; export what you filtered to as JSON or CSV. Reads the index `prma reindex` wrote and touches no network. Output `output/cache/review-missing.json`; the same build is the Rebuild button on the page. **Slow**: ~4 minutes for a pass over 97,000 abstracts, so — like `/review` — it is never run on the way to serving the page.
