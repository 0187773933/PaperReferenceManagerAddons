# Paper Reference Manager Addons

## Addons

1. `prma` : alias for `prma server --watch` — launches the live server (exists endpoint + dashboard) with the background auto-processing worker on. (Run `prma server` without bare-command for the server with `--watch` off.) Or `prma --exists` for **minimal mode** — the userscript endpoint and nothing else (see `prma server --exists` below).
1. `prma main` : the base pipeline — refresh the snapshot, then update the OpenAlex cache (meta + cited-by + references) for **every** library paper. This was the old no-subcommand default.
1. `prma missing` : generates missing.xlsx
2. `prma server` : runs the local HTTP server — the 'exists' endpoint for browser userscripts (`POST /exists`) **and** the full-text-search dashboard (`GET /`) for the **external papers you don't have**: works your library cites but you're missing, and works that cite your library. (Your own papers live in Zotero — they're indexed only for identity, to know what to exclude.) **Search** folds the text and your query the same way before matching — accents stripped and every punctuation mark (colons, slashes, hyphens, en/em dashes, curly quotes) flattened — so `MindAlign: Decoding Inner Speech`, `EEG–fMRI` and a pasted `10.1002/(SICI)1099-1492(199908)12:5` all find their paper (DOI, record key and journal are searchable too). Results are **ranked by relevance** by default whenever there's a query: the query as the *title* outranks the query buried on page 9 of a much-cited paper, with citations only breaking ties (click any column to rank your own way). If nothing matches at all, it falls back to the closest titles and says so. The dashboard serves the index that `prma reindex` persists to disk: it loads instantly and auto-reloads when you re-run reindex. If no index exists yet, it builds one lazily on first open. Pass `--watch` for **live processing**: a background worker detects papers you add to Zotero/Mendeley, runs the full per-paper suite on each (openalex → yolo → ocr → images → methods → code → md), and rebuilds the index so new papers appear automatically — the dashboard shows a live progress toast (polled from `GET /api/jobs`). Add `--watch-summarize` to also run the LLM summary on each. The same server hosts two **hand-curation boards** for building your premier-reference list by hand: search your library from the page (`↵` or double-click a hit adds it), drag rows to sort them, tag each with modalities (autocompleted from `config/methods.py`, pre-filled from the `prma modalities` stamp) plus your own click-to-paint tags, type into as many free-text columns as you want, delete anything with one click (the toast undoes it), and import / export the whole thing as CSV — every row carrying the same DOI / proxy / PDF / figures / MD / Methods links the dashboard shows. The boards' search **matches titles** by default (`mode=title` on `GET /api/search`): type any piece of a title and the closest titles come back, best first — nothing has to match exactly, so a typo, a missing word or two words the wrong way round still land the paper (a pasted DOI or record key jumps straight to it), and the dropdown switches to the dashboard's boolean full-text search when you want to hunt a phrase instead of a paper. Both boards **number every row and let you type into that number**: press `↵` and the paper goes to that position (its tier's, on `/tiers`) — no scrolling, no dragging. And you can **click a row to select it** (`⌘`-click adds another, `⇧`-click takes the range) and then click chips at the top to flip tags / modalities on and off the whole selection; with nothing selected, clicking a chip still arms it for click-to-paint, and `Esc` clears either. `🔎 Filter` turns that same chip bar into a **filter** — click tags and the board narrows to the papers carrying them (`any` / `all` switches whether one is enough), on top of the text box that matches anything typed anywhere in a row. Every tag and modality is drawn in **its own pastel**, so a row's chips are a pattern you read at a glance rather than five words you parse: a new one takes the next unused colour by itself, `🎨 Colours` is where you change them, and the choice lives in the document (`vocab.tags` / `vocab.mods`) so it follows the board to every browser. The chip bar itself is **rearrangeable by hand** — drag a chip along it and it stays where you put it, so you can group the ones you think of together (a chip only moves within its own bar; modalities and tags are separate vocabularies). That order is `vocab.tags` / `vocab.mods` order, i.e. part of the document, so a grouping you build is the same in every browser and after a restart, and a plain click still arms / filters / tags as before. Both boards also **import somebody else's bibliography**: `📋 Import refs` takes a reference list **pasted** in, or a **`.docx` / `.txt`** dropped on the panel, and reads it back into papers (`src/db/refparse.py` — numbered or not, AMA / Vancouver / APA / IEEE, wrapped across lines or one paragraph each; a `.docx` is unzipped and read server-side, so nothing has to be converted first). Each reference is resolved against your library by DOI, then by title, so one you already have arrives carrying **its real key** — every DOI / PDF / figures / MD / Methods link works, and its `prma modalities` stamp is pre-filled — while the rest keep whatever the parse got, picking up a WID and an open-access PDF url from the missing-paper pools where one matches. **Only what's new is taken**: anything already on the board, or already staged, is counted and skipped, so re-pasting a list you've grown brings in the difference and nothing else. Nothing lands on the board itself — it goes to a **staging shelf** above it, out of the sort and out of every tier, where you fix a mis-parsed title, tag rows one at a time or check several and tag them together, and only then press `＋ Add` (to the bottom of the sort list, or the bottom of the `◉ target` tier). A staged row is **the row it is about to become** — same chips *and the same free-text columns* — so a note you have while reading a reference is typed once, on the shelf, and rides onto the board with it; and **adding leaves you on the shelf** (the row flashes wherever it landed, but the page doesn't chase it), so working down an imported list is one pass instead of a scroll back for every row. The shelf is part of the document (`staging`), so a reload — or the other tab — still has it, and a CSV *Replace everything* leaves it alone. Neither board can lose what you typed into it: every change is mirrored into the browser and only dropped once the server confirms the save, a failed save retries by itself, closing the tab pushes one last copy out, and the next load **offers to restore** anything that never made it — while on disk each document is written atomically and, if a crash ever leaves one unreadable, recovered from its newest history snapshot instead of coming back empty. A row's chips are stored and shown **alphabetically**, so a paper reads the same way every time you look at it, and titles on both boards are plain text — as links they took the browser's visited colour the moment you opened a paper from any other prma page, so the link strip under each title is what opens it. **`GET /sort`** is one numbered list in the order *you* drag it into — no groups: what a paper is you say with tags (`fMRI`, `EEG`, both, or anything you invent, all saved with the board), where it sits you say by dragging. A paper added from search arrives already tagged from its Methods stamp. Tagging never reorders anything unless you turn on `⇥ Auto-move`, and `⇅ Order by…` reorders the whole list once (by tags, year, citations, title, date added) with an undo. **`GET /tiers`** is the sibling with buckets: tiers you place papers into, ranked S–D or whatever you rename them to. They keep separate documents (`output/cache/sort.json` / `tiers.json`, every replaced version kept under `output/cache/sort-history/` / `tiers-history/`), so they follow you across browsers like the figure-report picks do; `⇄ Pull from Tiers` copies the tier board's papers into the sort board. **`--exists` is minimal mode** — the opposite end: serve only what the browser userscripts poll (`POST /exists` + `GET /api/version`, plus `POST /refresh`) and nothing else. No dashboard index is loaded or built, no figure reports, and no per-paper processing forked off when you add papers to your library (it forces `--watch` off). Every other route answers `503` with an explanation instead. For when you just want the "do I already have this paper" coloring in the browser without running the whole pipeline. Works as `prma --exists` or `prma server --exists`.
3. `prma reindex` : refreshes the OpenAlex cache (snapshot + fetch new papers, download only), then (re)builds the dashboard's **own** full-text search index by streaming the OpenAlex cache off disk, and persists it. Independent of `missing.xlsx`. Incremental — adding papers only re-reads the new papers + their new references, not everything (`--full` to rebuild from scratch, `--skip-snapshot` to index the existing cache without re-fetching).
4. `prma snapshot` : creates local archive file
5. `prma yolo` : run doclayout yolo model on each pdf
6. `prma images` : generate individual images and a montage from figures and tables in each pdf
7. `prma ocr` : run ocr task on yolo blocks
8. `prma md` : generate markdown versions of each pdf
9. `prma text` : generate text versions of each pdf
10. `prma methods` : isolates methods sections of each pdf
11. `prma summarize` : runs summarization task on each pdf or section
12. `prma rollup` : generates a report from summarization tasks
13. `prma crawl` : attempts to crawl the OpenAlex graph
14. `prma code` : scans each paper's OpenAlex abstract + OCR text for **source-code / data links** (GitHub, GitLab, Bitbucket, OSF, Dryad, Zenodo, Figshare, Code Ocean, Hugging Face, …), reconstructing URLs the OCR split across lines and dropping dead/duplicate fragments. Pins the unique links on each record so the dashboard shows a sortable **Code** column (after Links, In-Library tab) and `prma md` can render a `## Source Code` section, and rolls everything up into `output/code/code.xlsx` (three sheets: *Links by Paper*, *By Paper*, and *Unique Links* — the last aggregating each link to the DOIs that cite it + a paper count; every per-paper sheet carries DOI / proxy / pdf links plus date-added and publication date). **GitHub / OSF enrichment:** if `config.yaml` has a `github.api_key`, it also fetches every unique GitHub repo's metadata + README (cached under `output/cache/github/`) and tags each by neuroimaging method (**fMRI / EEG / ECoG / fNIRS / MEG / PET / EMG**) — the *Unique Links* sheet gets a column per method (plus a combined *Methods* column on every sheet) so you can sort/filter to the fMRI repos first. With an `osfio.api_key` it does the same for every unique OSF (osf.io) node — resolving each GUID via the OSF API and pulling its metadata + Home wiki (cached under `output/cache/osf/`) — so OSF projects, registrations, and preprints get method-tagged too. **Method inference from citing papers:** a link is also tagged with the modalities of the papers that link it — the same keyword scan runs over each citing paper's abstract + isolated **methods section** (`prma methods` output, or the `## Methods` slice of the rendered md; *not* the full OCR, whose reference list would false-positive every cited modality) — so a repo whose README never names a method still inherits it from the fMRI / EEG / … studies that use it. The *Unique Links* method columns mark provenance: **✓** = confirmed in the repo/node README, **·** = inferred only from the citing papers. **OCR link repair:** GitHub links the OCR mangled (a truncated `…/Surfa` or merged `…-TOSTART-…`) 404 on fetch; rather than drop them, it lists the owner's *real* repos (cheap — the core API rate limit, not Search) and fuzzy-matches the broken name (`exact`/`prefix`/`fuzzy` tiers), then pins the corrected link so `code.xlsx` and the dashboard show the working repo (with an *OCR Fix* audit column / dashboard tooltip spelling out the original + match confidence, so a wrong guess is easy to spot). Runs OCR inline (idempotent) so it's one-stop. `--force` re-scans every paper and rebuilds the workbook from the **cached** GitHub/OSF data (no re-download — fast, for iterating on the scan/tagging logic); `--force-download` additionally re-fetches that cached metadata and re-runs link resolution over the network (the two are independent — combine them for a full refresh). Also runs automatically as the `code` stage of the per-paper suite (see below), so papers added under `prma server --watch` are scanned on the fly.
15. `prma process <doi-or-title>` : find ONE paper in your manager (by exact DOI or fuzzy title) and run the full per-paper suite on just it — snapshot → openalex → yolo → ocr → images → methods → code → md — then reindex so the dashboard refreshes. The library tasks are idempotent and scoped to the single paper, so this is fast. `--summarize` also runs the LLM summary. Same code path the server's `--watch` worker uses per newly-added paper.
16. `prma reprocess <doi-or-title>` : `prma process` with `--force` on — **redo** every stage on one paper instead of skipping the ones already done. Reach for it when you **replaced a paper's PDF** (the published version swapped in for the preprint / manuscript you first added): the DOI never changed, so the snapshot sees nothing new, every stage finds its old output and skips, and the server's `--watch` backlog counts the paper as done — nothing in the pipeline notices the new file on its own. It deletes what the pipeline derived for that paper (`output/md`, `output/methods`, `output/text`, its figure crops + montages under `output/images`, and the derived record fields — `yolo` / `sections` / `raw_text` / `images` / `code` / `modalities` / the `processed` stamp), then runs the suite normally so each stage rebuilds from the PDF on disk *now*. Identity (`doi` / `title` / `sources`) and the OpenAlex cache are untouched; LLM summaries are kept unless you also pass `--summarize`, which regenerates them. Prints the PDF path it's about to work from — worth a glance, since a Zotero item holding **several** PDFs resolves to the first one that exists on disk, not the newest. (Not to be confused with `prma reindex`, which rebuilds the dashboard's search index for the whole library and runs no pipeline stages.)

17. `prma review` : builds the **literature review** the server serves at **`GET /review`** — what `/sort` and `/images` *add up to*. Those two pages are judgements (this paper is worth keeping; this figure is worth looking at) and neither says anything about what the papers **contain**; this takes their union and reads the text `prma md` and `prma methods` already wrote. Every candidate is **screened against three criteria**, all of which must hold: fMRI/BOLD is the *dominant* modality in its methods (an EEG/MEG/ECoG/fNIRS paper that merely mentions fMRI is out), the paper **decodes** (fMRI in, stimulus / mental content / class label out — encoding models and MRI reconstruction / acceleration are out), and transformer or attention machinery sits inside the model **the authors built** (citing Vaswani in related work is not enough). What survives gets every architecture, acquisition and preprocessing detail its own text states pulled out — layer counts, heads, embedding dims, backbones, losses, optimiser, LR, TR, TE, voxel size, slices, atlas, smoothing, and forty-odd more — and **every value carries the verbatim sentence it was parsed from**, so nothing on the page has to be taken on trust; click a value and the quote opens under it. Values that are physically impossible for human fMRI (a 565 ms echo time, a 40 mm voxel) are dropped by plausibility gates, and where a paper states a parameter more than once the values are ranked by how often it says it. **A blank means the paper does not say it**, never that the value is zero, and the page prints those words rather than leaving a cell empty to be misread. Most deep-learning papers never state scanner settings at all — they say "we use NSD" and move on — so acquisition blanks are filled from a **consensus mined out of the whole corpus** for the public dataset that paper uses, marked *from dataset* and naming how many papers back it; a paper using several datasets is left blank rather than guessed. Hand-verified detail in `config/review-overrides.json` (keyed by the same DOI / record key the boards use) overrides the extraction and flags the row. The page **orders the list the way every other prma surface does** — recently added, publication date, year, citations, title, model name, each reversible — on top of the default (priority, then newest), and puts the citation count and the date the paper entered your library on the row itself, so a list ordered by a fact is a list you can see that fact in. (*Recently added* is prma's own `created_at`, the same date the figure reports' "Recently added" uses; the record doesn't carry Zotero's `dateAdded`. Papers missing a sort key always fall to the bottom rather than clumping at the top as a run of blanks, in either direction.) It **follows your light / dark setting** — the shared `prma-theme`, so flipping it here flips the dashboard and both boards too. It filters by priority (1 = inner/imagined speech, the bullseye), task category, and whether a paper is on the sort board, has picked figures, is human-curated or ships code; every row carries the same link strip as the rest of prma — DOI / Proxy / PDF / MD / Methods / **Figures** (the `prma images` montage), on the excluded rows too, where flicking through a borderline paper's figures is the fastest way to check the screener was right; it exports what you're looking at as JSON or CSV; and it shows **what was excluded and why**, with the **borderline** ones — dropped only for weak attention evidence — flagged, because that is where a false negative hides. Output `output/cache/review.json`; the same build is the Rebuild button on the page. **Slow**: a regex pass over every candidate's full text, minutes on a few hundred papers, so it is never run on the way to serving the page — the server hands you the last build, says when the boards have moved since, and rebuilds in the background while you watch the progress bar.
